Доставка, повторы и снимки

Что считается повтором​

Если отправитель не получил подтверждение доставки, он может повторно отправить событие. Получатель тогда видит несколько сообщений об одном действии. В другом случае пользователь действительно нажал на карточку дважды. Семантические поля и округлённое время могут совпасть, но действий будет два.

Идентичность события задаётся источником. В нашем договоре новое действие получает новый event_id, повтор доставки сохраняет его. Правило CloudEvents о паре source и id и возможности сохранения ID при повторной отправке описано в спецификации 1.0.2. Ни одинаковый ID вне своей области, ни одинаковый пользователь и объект сами по себе не задают универсальную дедупликацию.

Определение · Каноническое событие#

Пусть у доставок с одним ключом совпадают все смысловые поля, кроме времени получения. Каноническим представлением этого события назовём запись с минимальным received_at. Канонизацией набора доставок назовём замену каждой такой группы одной канонической записью с последующей устойчиво заданной сортировкой.

Минимальное время получения важно для восстановления знания: если копии поступили в 5 и 6, событие было известно уже в 5. Выбор последней копии искусственно сдвинул бы этот момент.

Одинаковый ключ с разным item_id, action или event_time — конфликт контракта, а не обычный повтор. В учебном алгоритме он останавливает обработку. Если источник поддерживает исправления событий, ему нужны отдельная семантика ревизий и время их доступности. Простое правило «оставить последнюю строку» смешивает исправление и повтор доставки.

Идемпотентность​

Теорема · Повторная обработка не меняет результат#

Пусть конечный набор EEE не содержит конфликтующих доставок одного ключа. Для определённой выше канонизации DDD выполняется

D(D(E))=D(E).D(D(E))=D(E).D(D(E))=D(E).

Перестановка входных доставок также не меняет результат, если порядок выхода определяется парой (received_at, event_id).

Доказательство

После первого применения каждый ключ представлен ровно одной записью с минимальным временем получения своей группы. Во втором применении группы одноэлементны: их минимумы и смысловые поля не меняются. Сортировка по той же паре воспроизводит тот же список. При перестановке исходного входа группы ключей и минимумы времени остаются прежними; при равенстве времени копии полностью совпадают. Поэтому выход также сохраняется.

□

Это свойство конкретного преобразования. Оно не доказывает, что событие было произведено ровно один раз, что все события доставлены или что любой внешний побочный эффект обработчика идемпотентен. Например, повторное увеличение счётчика в отдельной системе всё ещё требует собственного корректного протокола.

Снимок доступного знания​

Для момента экспорта ccc определим

Ec=D({ej:aej≤c}).E_c=D\bigl(\{e_j:a_{ej}\le c\}\bigr).Ec​=D({ej​:aej​≤c}).

Сначала выбираются доставки, известные к моменту среза, затем выполняется канонизация. В примере граница включена: считаем, что экспорт выполняется после обработки всех доставок с received_at=c. Это правило экспорта результата, а не разрешение использовать будущие относительно решения признаки.

Фильтрация event_time<=c недостаточна. Дочитывание i3 имеет время действия 16 и первую доставку 20. В снимке на 17 оно отсутствует, хотя уже произошло. Сортировка по времени действия не делает его доступным раньше доставки.

delivery.py
"""Снимок по времени получения и идемпотентная дедупликация."""
from dataclasses import fields
from schema import Event, validate


def signature(event):
    return tuple(getattr(event, field.name) for field in fields(Event)
                 if field.name != "received_at")


def canonicalize(events):
    by_id = {}
    for event in events:
        validate(event)
        previous = by_id.get(event.event_id)
        if previous is not None and signature(previous) != signature(event):
            raise ValueError(f"Конфликт содержимого event_id={event.event_id}")
        if previous is None or event.received_at < previous.received_at:
            by_id[event.event_id] = event
    return sorted(by_id.values(), key=lambda event: (event.received_at, event.event_id))


def snapshot(events, cutoff):
    if type(cutoff) is not int or cutoff < 0:
        raise ValueError("cutoff должен быть неотрицательным целым")
    visible = [event for event in events if event.received_at <= cutoff]
    return canonicalize(visible)

signature строит кортеж всех полей события, кроме received_at. Словарь хранит одну запись на ключ. При конфликте выбрасывается ошибка; иначе выбирается минимальная отметка получения. Сортируется уже канонический список.

Важен порядок операций внутри snapshot. Если конфликтующая копия пришла только в 50, она не должна участвовать в проверке снимка на 12. При этом общий парсер учебного файла проверяет формат всех входных записей; снимок не обещает игнорировать любые ошибки формата в остальной выгрузке.

При nnn доставках и mmm уникальных событиях ожидаемая стоимость словарного прохода составляет O(n)O(n)O(n) при обычном предположении о хеш-таблице, сортировка требует O(mlog⁡m)O(m\log m)O(mlogm), хранение канонических записей — O(m)O(m)O(m). Это обработка конечной выгрузки, а не алгоритм бесконечного потока с ограниченной памятью.

Поздние события и watermark​

В потоке время действия и время обработки различаются, а порядок прихода может не совпадать с порядком действий. Watermark используют для оценки прогресса по времени событий. В Apache Beam Programming Guide отдельно описаны поздние данные и их обработка после продвижения watermark.

Поэтому watermark или «прошло пять минут» нельзя без дополнительной гарантии трактовать как доказательство отсутствия любого будущего события из прошлого. Правило ожидания, полнота регистрации, допустимая задержка и обработка нарушений — разные части контракта. В следующей главе о метках мы намеренно введём строгую границу задержки как предпосылку, а не выведем её из watermark.

Упражнения​

Упражнение · Ошибка последней копии#

Одно событие получено в 5 и 9. Канонизацию всей выгрузки выполнили по последней копии, затем отфильтровали по received_at<=6. Что произойдёт?

Разбор

Событие исчезнет из снимка, хотя первая доставка была известна в 5. Выбор минимальной отметки и фильтрация доступных доставок сохраняют правильное знание. Последняя копия не обозначает момент первого появления события.

Упражнение · Настоящий повтор действия#

Два события имеют разные ID, но одинаковые user_id, item_id, action и время в минутах. Следует ли автоматически объединить их? Что необходимо для более сильного правила дедупликации?

Разбор

По нашему контракту это разные события. Для объединения нужно основание в механизме производства данных: например, установленный дефект, создающий несколько ID одному действию, и проверяемое правило его исправления. Одного совпадения полей недостаточно; иначе исчезнут реальные повторные действия.
