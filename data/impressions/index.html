Показы, действия и соединения

От кандидата до наблюдаемой карточки​

Объект может быть доступен для рекомендации, отобран в кандидаты, включён в выдачу, отправлен клиенту, отрисован, оказаться в видимой области экрана и привлечь внимание. Это последовательность разных состояний. Конкретная система может регистрировать только некоторые из них.

В нашей схеме impression означает подтверждённую отрисовку в целевой позиции. Мы не выводим из неё факт внимания. Для другого источника потребуется прочитать его определение показа; одноимённые поля не гарантируют одинаковое измерение.

Полезно различать три набора для запроса qqq: доступные объекты AqA_qAq​, отобранные кандидаты CqC_qCq​ и упорядоченную выдачу LqL_qLq​. Если система действительно строит их вложенно, то Lq⊆Cq⊆AqL_q\subseteq C_q\subseteq A_qLq​⊆Cq​⊆Aq​ при рассмотрении множеств объектов. Это условие архитектуры, а не свойство произвольной выгрузки. Клиентские подтверждённые показы могут охватывать лишь часть LqL_qLq​.

Если в данных сохранены только показы, из них нельзя восстановить полный AqA_qAq​ или CqC_qCq​. Если сохранена финальная оценка объекта, она не является вероятностью выбора политикой. Для воспроизведения решения могут понадобиться версия модели, фильтры, доступность, порядок выдачи и правила случайного выбора. Наличие одного score всех этих сведений не заменяет.

Почему нужен отдельный ID показа​

Пользователь может увидеть статью A утром и вечером. Соединение дочитывания только по (user_id, item_id) найдёт оба показа. Выбор ближайшего показа по времени создаст правило атрибуции; он не восстановит отсутствующую ссылку с гарантией.

В учебном источнике ответ уже содержит impression_id, присвоенный при показе. Мы требуем согласованности пользователя, запроса, объекта и позиции. К одному показу допустимы несколько отдельных кликов и дочитываний. Для бинарной метки они позднее будут свёрнуты операцией «существует», а не превращены в несколько показов.

Ссылка устанавливает зарегистрированную атрибуцию. Она не доказывает, что именно этот показ причинно вызвал действие. Это особенно существенно для заказов с несколькими касаниями: first-touch и last-touch — правила отнесения результата, а не автоматические оценки причинного вклада.

Как соединение размножает строки​

Напомним табличные соединения. Если каталог содержит несколько строк одного item_id, обычный JOIN по нему размножает события. Это свойство операции, а не случайность библиотеки.

Теорема · Число строк inner join#

Пусть конечные таблицы E,DE,DE,D соединяются по равенству непустого, не содержащего NULL ключа. Через nE(k)n_E(k)nE​(k) и nD(k)n_D(k)nD​(k) обозначим число строк с ключом kkk. Тогда с учётом повторений строк

∣E⋈D∣=∑knE(k)nD(k).|E\Join D|=\sum_k n_E(k)n_D(k).∣E⋈D∣=k∑​nE​(k)nD​(k).
Доказательство

Для фиксированного ключа каждая из nE(k)n_E(k)nE​(k) строк первой таблицы соединяется с каждой из nD(k)n_D(k)nD​(k) строк второй. Получается nE(k)nD(k)n_E(k)n_D(k)nE​(k)nD​(k) пар. Группы по различным ключам не пересекаются; сумма их размеров даёт весь результат.

□

Если в событиях две строки A и одна B, а в каталоге две версии A и одна B, результат содержит 2⋅2+1⋅1=52\cdot2+1\cdot1=52⋅2+1⋅1=5 строк вместо трёх. Для сохранения ровно одной строки на событие нужны и уникальность подходящей записи каталога, и покрытие каждого события. Отсутствие подходящей записи при INNER JOIN удалит строку. LEFT JOIN сохранит её с пропусками, но не исправит неоднозначность нескольких совпадений.

Для исторического каталога ключом соединения служит не только равенство item_id: нужны условия принадлежности двум временным интервалам. Ровно одна подходящая версия проверяется до использования результата.

Связывание событий с нуля​

linking.py
"""Связь ответов с уникальным показом; осиротевшие ответы сохраняются в отчёте."""


def link(events):
    impressions = {}
    request_positions = set()
    request_users = {}
    for event in events:
        if event.action != "impression":
            continue
        if event.impression_id in impressions:
            raise ValueError("Для impression_id найдено несколько событий показа")
        previous_user = request_users.setdefault(event.request_id, event.user_id)
        if previous_user != event.user_id:
            raise ValueError("Один request_id связан с разными аккаунтами")
        position = (event.request_id, event.position)
        if position in request_positions:
            raise ValueError("Повторная позиция внутри запроса")
        request_positions.add(position)
        impressions[event.impression_id] = event

    responses = {key: [] for key in impressions}
    orphans = []
    for event in events:
        if event.action == "impression":
            continue
        impression = impressions.get(event.impression_id)
        if impression is None:
            orphans.append(event)
            continue
        for name in ("user_id", "request_id", "item_id", "position"):
            if getattr(event, name) != getattr(impression, name):
                raise ValueError(f"Ответ не согласован с показом по {name}")
        if event.event_time < impression.event_time:
            raise ValueError("Ответ раньше показа в общей шкале примера")
        responses[event.impression_id].append(event)
    return impressions, responses, orphans

На вход подаётся уже канонический журнал. Первый проход строит словарь показов и проверяет, что одному impression_id соответствует одно событие impression. В нашем договоре один request_id относится к одному аккаунту, а пара (request_id, position) не повторяется среди показов. Резервирование позиции выполняется множеством.

Во втором проходе каждый ответ попадает в список соответствующего показа. Несовпадение ключевых атрибутов или ответ раньше показа в общей временной шкале вызывает ошибку. Ответ без видимого показа сохраняется отдельно как orphan; функция не отбрасывает его молча.

Такое отсутствие может быть постоянной ошибкой, фильтрацией части источника или временной ситуацией: ответ уже доставлен, подтверждение показа ещё нет. Причину нельзя определить по одному внешнему ключу. Итоговый сборщик нашего примера останавливается при наличии orphan; потоковая система могла бы сначала ожидать позднюю запись и отдельно учитывать неразрешённые случаи.

При словарном доступе ожидаемая стоимость двух проходов — O(n)O(n)O(n) по числу событий. Поиск «все ответы для каждого показа» полным сканированием журнала дал бы O(np)O(np)O(np) при ppp показах. Здесь индексирование одновременно делает правило связи явным и устраняет этот лишний повторный поиск.

Знаменатель зависит от постановки​

Для доли показов с хотя бы одним кликом знаменатель — число допустимых показов, числитель — число таких показов с кликом. Для числа кликов на показ числитель считает события; при повторных кликах отношение способно превысить единицу. Обе величины определимы, но это разные метрики.

Если карточка была отправлена, но не отрисована, включение её в знаменатель меняет измерение. Если известны только положительные пары, добавление всех отсутствующих пар как «показов без клика» создаёт вымышленные экспозиции. В части об оценке мы будем задавать метрики вместе с единицей, допустимым множеством и механизмом наблюдения.

Упражнения​

Упражнение · Две строки ответа#

Есть один показ и два отдельных клика, корректно связанных с ним. Чему равны число кликов на показ и доля показов хотя бы с одним кликом?

Разбор

Первое отношение равно 2, второе — 1. Перед соединением бинарной метки ответы агрегируются до одной строки на показ по правилу существования клика. Если оставить две строки и затем посчитать их как два показа, будет потеряна исходная единица наблюдения.

Упражнение · Пропуск и размножение#

В EEE три строки A и две B; в DDD две строки A и ни одной B. Сколько строк даст INNER JOIN? Доказывает ли результат того же размера, что EEE, отсутствие ошибок соединения в общем случае?

Разбор

Получится 3⋅2+2⋅0=63\cdot2+2\cdot0=63⋅2+2⋅0=6 строк. Совпадение общего размера в другом примере не доказывало бы корректность: потери одних ключей могут компенсироваться размножением других. Нужны проверки мощности совпадений для каждой исходной единицы, а не только общий count.
