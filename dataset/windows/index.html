Оконные признаки и SQL

Явно определить множество истории​

Для запроса пользователя uuu в ttt используем завершения чтения с event time в [t−W,t)[t-W,t)[t−W,t) и временем доступности не позже ttt. В нашем примере доступность равна доставке. История определяется для каждого запроса, а не единственным общим срезом запуска сборщика:

Hu(t;W)={e:ue=u, ke=finish, t−W≤te<t, ae≤t}.\mathcal H_u(t;W)=\{e:u_e=u,\ k_e=\text{finish},\ t-W\le t_e<t,\ a_e\le t\}.Hu​(t;W)={e:ue​=u, ke​=finish, t−W≤te​<t, ae​≤t}.

Текущий показ и его исход не могут попасть в эту историю по правой границе. Событие ровно на левой границе включается. Если зарегистрирован строгий порядок событий внутри одинакового timestamp, правило можно уточнить им; в этой реализации все исходы с te=tt_e=tte​=t консервативно исключаются.

Определение · Счётчики и давность#

Nu(t)=∣Hu(t;W)∣N_u(t)=|\mathcal H_u(t;W)|Nu​(t)=∣Hu​(t;W)∣, Nui(t)=∑e∈Hu(t;W)1{ie=i}N_{ui}(t)=\sum_{e\in\mathcal H_u(t;W)}\mathbf1\{i_e=i\}Nui​(t)=∑e∈Hu​(t;W)​1{ie​=i}. При непустой истории Ru(t)=t−max⁡e∈Hu(t;W)teR_u(t)=t-\max_{e\in\mathcal H_u(t;W)}t_eRu​(t)=t−maxe∈Hu​(t;W)​te​. При пустой истории давность не определена; хранится пропуск и индикатор отсутствия.

Значение recency=0 означало бы событие сейчас; оно не является синонимом отсутствия событий. При заполнении пропуска большим числом нужна определённая константа и mask. Если константа оценивается по распределению, её выбирают только на обучающей части.

Проверка вручную​

В момент 10 при W=4W=4W=4 известны события: (5,5), (6,6), (9,11), (9,10), (10,10), где пара — event time и доставка. Включаются события 6 и второе событие 9. Поэтому Nu=2N_u=2Nu​=2, Ru=1R_u=1Ru​=1. Первое слишком старое, другое событие 9 недоступно, событие 10 лежит на исключённой правой границе.

Лемма · Вложенные окна#

Для одного момента ttt и одинакового правила доступности при 0<W1≤W20<W_1\le W_20<W1​≤W2​ выполняется Hu(t;W1)⊆Hu(t;W2)\mathcal H_u(t;W_1)\subseteq\mathcal H_u(t;W_2)Hu​(t;W1​)⊆Hu​(t;W2​), поэтому счётчики не убывают при увеличении окна. Для разных моментов ttt такой монотонности нет.

Доказательство

Интервал [t−W1,t)[t-W_1,t)[t−W1​,t) содержится в [t−W2,t)[t-W_2,t)[t−W2​,t); остальные предикаты совпадают. В более позднем запросе левые границы сдвигаются, поэтому старые события могут выйти из окна.

SQL: сначала корректность множества​

В WINDOW_SQL ниже LEFT JOIN сохраняет запросы без истории. Условия истории стоят в ON: перенос условия на правую таблицу в WHERE удалил бы пустые запросы. COUNT(a.id) даёт 0 при отсутствии совпадений; COUNT(*) дал бы 1 из-за строки LEFT JOIN. MAX(a.t) сохраняет NULL для пустой истории.

features.py
"""Прямые реализации для проверки временной семантики, а не промышленной скорости."""
import sqlite3
from contextlib import closing
from journal import version_at


def session_ids(requests, gap):
    if gap < 0:
        raise ValueError("gap должен быть неотрицательным")
    result, previous, counters = {}, {}, {}
    for r in sorted(requests, key=lambda r: (r["user"], r["t"], r["id"])):
        user = r["user"]
        if user not in previous or r["t"]-previous[user] > gap:
            counters[user] = counters.get(user, 0) + 1
        result[r["id"]] = (user, counters[user])
        previous[user] = r["t"]
    return result


def session_prefix(requests, current, gap=12):
    visible = [r for r in requests if r["user"] == current["user"]
               and r["t"] <= current["t"] and r["received"] <= current["t"]]
    ids = session_ids(visible, gap)
    same = [r for r in visible if ids[r["id"]] == ids[current["id"]]]
    return len(same), current["t"]-min(r["t"] for r in same)


def history(actions, request, window=24):
    if window <= 0:
        raise ValueError("window должен быть положительным")
    t = request["t"]
    return [a for a in actions if a["user"] == request["user"]
            and a["kind"] == "finish" and t-window <= a["t"] < t
            and a["received"] <= t]


def feature_row(data, request, item, window=24):
    events = history(data["actions"], request, window)
    version = version_at(data["versions"], item, request["t"])
    if version is None:
        raise ValueError("Нет доступной версии")
    count, age = session_prefix(data["requests"], request)
    recency = request["t"]-max(a["t"] for a in events) if events else None
    return dict(user_finishes=len(events), item_finishes=sum(a["item"] == item for a in events),
                recency=recency, recency_missing=int(recency is None),
                session_requests=count, session_age=age,
                topic=version["topic"], revision=version["revision"])


WINDOW_SQL = """
SELECT r.id, COUNT(a.id) AS n, MAX(a.t) AS last_t
FROM requests AS r
LEFT JOIN actions AS a ON a.user=r.user AND a.kind='finish'
  AND a.t >= r.t-? AND a.t < r.t AND a.received <= r.t
GROUP BY r.id
ORDER BY r.id
"""


def sql_windows(data, window=24):
    with closing(sqlite3.connect(":memory:")) as con:
        con.execute("CREATE TABLE requests(id TEXT, user TEXT, t INTEGER)")
        con.execute("CREATE TABLE actions(id TEXT, user TEXT, t INTEGER, received INTEGER, kind TEXT)")
        con.executemany("INSERT INTO requests VALUES(:id,:user,:t)", data["requests"])
        con.executemany("INSERT INTO actions VALUES(:id,:user,:t,:received,:kind)", data["actions"])
        return con.execute(WINDOW_SQL, (window,)).fetchall()

history возвращает доступные события. feature_row добавляет пользовательский и парный счётчики, давность, признаки префикса сессии и версию темы объекта. В примере revision сохраняется для аудита; технический идентификатор ревизии не подаётся в baseline как числовой сигнал.

sql_windows создаёт независимую SQLite-проверку счётчика и последнего времени для всех запросов. Соединение закрывается явно через closing; память и соединения не остаются после расчёта.

Почему не достаточно ROWS​

Окно ROWS BETWEEN 10 PRECEDING AND 1 PRECEDING означает десять строк, а не десять минут. При нерегулярных событиях это разные объекты. Кроме того, соседние строки по event time могут содержать поздние доставки. Один LAG после окончательной сортировки не восстанавливает доступный онлайн-префикс.

Для временных диапазонов SQL поддерживает собственные frame-семантики; в частности RANGE ... CURRENT ROW может включать все строки с одинаковым значением сортировки. Нельзя предполагать исключение текущего события без чтения правил конкретного движка. Здесь условный JOIN выбран потому, что обе границы и доставка видны непосредственно. Семантика frame и peer-строк описана в официальной документации SQLite.

Другие семейства признаков​

Тот же контракт задаёт число показов, уникальных объектов, среднее dwell time, частоты тем, время с последнего заказа и скорости изменения активности. Для доли завершений знаменателем должны быть соответствующие полностью наблюдаемые показы; деление на все недавние показы с ещё незрелыми исходами смешивает завершённое наблюдение с ожидающим.

Предварительная агрегация по часам ускоряет расчёт, но может потерять точную границу окна и время доступности. При таком ускорении нужно явно задать точность и пересчитывать пограничные bucket. Для популярности объекта действуют те же требования, хотя признак агрегируется по всем пользователям.

Прямой просмотр всех EEE действий для QQQ запросов стоит O(QE)O(QE)O(QE). Сессионная часть здесь дополнительно пересортировывает префиксы. Это эталон семантики для маленького журнала. В большой системе нужны индексы, сортировка и потоковое состояние; они должны воспроизводить этот результат при одинаковом контракте, а не менять его ради удобства.

Упражнение · Пустая история

В LEFT JOIN нет совпадений. Чему равны COUNT(*), COUNT(a.id) и MAX(a.t)? Какой результат нужен для счётчика событий?

Разбор

Значения 1, 0 и NULL. Счётчик событий равен 0; последнее время отсутствует. Это пример, где корректное сохранение строки ещё не гарантирует корректность агрегата.

Упражнение · Незрелый знаменатель

За последние десять минут было 10 показов, из них 4 полностью наблюдаемы и дали 2 завершения. Можно ли назвать 2/102/102/10 оценкой доли завершений по зрелым показам?

Разбор

Нет. По четырём зрелым показам доля 2/42/42/4. Значение 2/102/102/10 описывает число уже доставленных единиц на все недавние показы; это другой измеряемый объект. Даже 2/42/42/4 относится к выбранной зрелой когорте, а не автоматически ко всем свежим показам.
