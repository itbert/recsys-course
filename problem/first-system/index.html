Первая система с нуля

Реализуем рекомендатель статей по числу прошлых дочитываний. Его назначение — проверить соответствие постановки, данных и решения на примере, который можно полностью воспроизвести. Обучение сложной модели для этого не требуется.

Спецификация​

Вход: каталог статей, журнал событий, идентификатор пользователя uuu, момент запроса ttt и максимальная длина выдачи KKK. Время представлено целыми числами, обозначающими последовательные условные моменты.

Примем следующие правила:

  1. Для решения используются только события с timestamp < now. В учебном журнале событие считается известным системе в момент своего совершения. На реальных данных потребуется также время поступления.
  2. Статья доступна на полуинтервале от available_from включительно до available_until исключительно. Отсутствие правой границы означает, что снятие не запланировано.
  3. Уже дочитанные данным пользователем статьи исключаются. Клик без дочитывания исключения не создаёт.
  4. Скоринг равен числу прошлых событий finish для статьи по всем пользователям.
  5. Выдача содержит до KKK объектов с наибольшим скорингом. Ничья разрешается по идентификатору.

Это глобальный скоринг с персональным фильтром истории. Предпочтения разных пользователей в нём не моделируются. Повторные события finish, если они есть в журнале, считаются отдельно; дедупликация и подсчёт уникальных читателей — другие правила.

Математическая запись​

Для события eee обозначим время как tet_ete​, объект как iei_eie​, пользователя как ueu_eue​, тип как aea_eae​. Введём индикатор 1[P]\mathbf{1}[P]1[P], равный единице при истинности условия PPP и нулю иначе.

Тогда оценка статьи равна

st(i)=∑e∈H1[te<t] 1[ie=i] 1[ae=finish].s_t(i)=\sum_{e\in H} \mathbf{1}[t_e<t]\, \mathbf{1}[i_e=i]\, \mathbf{1}[a_e=\text{finish}].st​(i)=e∈H∑​1[te​<t]1[ie​=i]1[ae​=finish].

Множество уже дочитанных пользователем объектов:

Su,t={ie: te<t, ue=u, ae=finish}.S_{u,t}=\{i_e:\ t_e<t,\ u_e=u,\ a_e=\text{finish}\}.Su,t​={ie​: te​<t, ue​=u, ae​=finish}.

Из доступных к моменту ttt статей удаляется Su,tS_{u,t}Su,t​. Оставшиеся сортируются по st(i)s_t(i)st​(i) по убыванию, а при равенстве — по идентификатору по возрастанию. Этот порядок полностью определяет результат.

Полный код​

Требуется Python 3.10 или новее. Внешних библиотек, сетевых запросов и загрузки данных нет. Код ниже можно скопировать в recommender.py и выполнить командой python3 recommender.py.

recommender.py
"""Учебная рекомендация статей по прошлым дочитываниям. Python 3.10+."""

from collections import Counter
from dataclasses import dataclass


@dataclass(frozen=True)
class Item:
    item_id: str
    title: str
    available_from: int = 0
    available_until: int | None = None


@dataclass(frozen=True)
class Event:
    timestamp: int
    user_id: str
    item_id: str
    action: str


def recommend(
    catalog: list[Item],
    events: list[Event],
    user_id: str,
    now: int,
    k: int,
) -> list[tuple[Item, int]]:
    if k < 0:
        raise ValueError("k должно быть неотрицательным")

    past = [event for event in events if event.timestamp < now]
    finishes = [event for event in past if event.action == "finish"]
    counts = Counter(event.item_id for event in finishes)
    seen = {event.item_id for event in finishes if event.user_id == user_id}

    candidates = [
        item for item in catalog
        if item.available_from <= now
        and (item.available_until is None or now < item.available_until)
        and item.item_id not in seen
    ]
    ranked = sorted(candidates, key=lambda item: (-counts[item.item_id], item.item_id))
    return [(item, counts[item.item_id]) for item in ranked[:k]]


CATALOG = [
    Item("A", "Короткая новость"),
    Item("B", "Разбор с примером"),
    Item("C", "Подробный обзор"),
    Item("D", "Вводная заметка"),
    Item("E", "Снятая с публикации статья", available_until=9),
    Item("F", "Будущая публикация", available_from=12),
]

EVENTS = [
    Event(1, "u1", "A", "finish"),
    Event(2, "u2", "A", "finish"),
    Event(3, "u3", "A", "finish"),
    Event(4, "u2", "B", "finish"),
    Event(5, "u3", "B", "finish"),
    Event(6, "u2", "C", "finish"),
    Event(7, "u4", "E", "finish"),
    Event(8, "u4", "D", "click"),
    Event(10, "u5", "D", "finish"),
    Event(11, "u6", "D", "finish"),
]


if __name__ == "__main__":
    for item, count in recommend(CATALOG, EVENTS, user_id="u1", now=10, k=2):
        print(f"{item.item_id}: {item.title} — прошлых дочитываний: {count}")

Код на странице включается из того же исходного файла, который используется при проверке примера. Отдельная копия фрагмента вручную не поддерживается.

Устройство данных и синтаксис​

Item и Event — записи с именованными полями. Декоратор @dataclass создаёт для них стандартный конструктор; frozen=True запрещает обычное изменение полей уже созданной записи. Это удобство представления данных, а не часть алгоритма ранжирования.

Аннотация str обозначает строку, int — целое число. int | None разрешает либо целое, либо отсутствие значения. list[tuple[Item, int]] описывает результат: список пар «статья, её счётчик». Аннотации объясняют интерфейс функции и поддерживают инструменты проверки, но сами по себе не валидируют произвольные входные данные во время исполнения.

CATALOG и EVENTS — встроенные синтетические данные. Конструкция if __name__ == "__main__" запускает печать результата при выполнении файла, сохраняя возможность импортировать функцию отдельно.

Разбор алгоритма​

История до момента решения​

past = [event for event in events if event.timestamp < now]

Это списковое включение: проход по событиям с сохранением только тех, которые удовлетворяют временному условию. Событие с временем, равным now, исключено по спецификации. Если нужен более точный порядок внутри одной временной отметки, его следует задать отдельным полем или более точным временем.

Целевое событие и счётчики​

finishes = [event for event in past if event.action == "finish"]
counts = Counter(event.item_id for event in finishes)

Первая строка выбирает дочитывания. Вторая передаёт их идентификаторы объектов в Counter из стандартного модуля collections. Он подсчитывает число вхождений каждого идентификатора. Для отсутствующего ключа Counter возвращает ноль, поэтому статья без дочитываний остаётся допустимой с нулевой оценкой.

Выражение в круглых скобках — генератор: идентификаторы передаются по одному без отдельного списка. Здесь счётчик использует действия всех пользователей. В нём нет деления на число показов: это не CTR и не оценка вероятности.

История пользователя​

seen = {event.item_id for event in finishes if event.user_id == user_id}

Фигурные скобки создают множество. Оно содержит уникальные идентификаторы дочитанных пользователем статей. Проверка принадлежности множеству позволяет исключать их при проходе по каталогу. Использование множества не изменяет глобальные счётчики: это отдельная операция с отдельным назначением.

Доступность​

Три условия в candidates реализуют спецификацию: публикация уже началась, снятие ещё не наступило и статья отсутствует в seen. Условие с or не сравнивает now с None: если правая граница отсутствует, левая часть уже истинна.

В этом небольшом примере candidates содержит все допустимые объекты. Отдельного приближённого retrieval нет. Это позволяет проверить задачу без дополнительной ошибки отбора.

Порядок и ограничение размера​

ranked = sorted(candidates, key=lambda item: (-counts[item.item_id], item.item_id))
return [(item, counts[item.item_id]) for item in ranked[:k]]

sorted сортирует по возрастанию ключа. Поэтому первый элемент ключа — отрицательный счётчик: больший исходный счётчик оказывается раньше. Второй элемент — идентификатор для разрешения ничьей. lambda задаёт короткую функцию вычисления этого ключа.

Срез [:k] сохраняет не больше k объектов. При k=0 результат пуст; если кандидатов меньше, возвращаются все. Отрицательное k отвергается явно: без этой проверки срез имел бы другой смысл и нарушал спецификацию.

Проверка результата вручную​

При now=10 счётчики и ограничения имеют вид:

СтатьяПрошлых дочитыванийДопустима для u1?Основание
A3Нетu1 уже дочитал A
B2ДаОпубликована, ранее не дочитана
C1ДаОпубликована, ранее не дочитана
D0ДаПрошлый клик не является дочитыванием
E1НетСнята в момент 9
F0НетБудет опубликована в момент 12

События D с временами 10 и 11 не входят в историю. Поэтому при k=2 функция выводит:

B: Разбор с примером — прошлых дочитываний: 2
C: Подробный обзор — прошлых дочитываний: 1

Совпадение идентификаторов B и C с примером оптимизации дочитываний из предыдущих глав случайно: здесь используется другой, исторический скоринг. Пример не подтверждает, что популярность восстанавливает заданные там вероятности.

Корректность и сложность​

В реализации выполняются следующие свойства:

  • каждый возвращённый объект удовлетворяет условиям доступности и отсутствует в истории дочитываний пользователя;
  • добавление событий с временем не меньше now не меняет результат;
  • оценки совпадают с числом подходящих событий finish;
  • длина не превосходит k, а порядок детерминирован для уникальных идентификаторов каталога.

Первые три свойства следуют из соответствующих фильтров и определения Counter. Последнее следует из сортировки по заданному ключу и среза. Уникальность идентификаторов каталога — предпосылка входных данных, а не автоматически выполненная проверка.

Пусть mmm — число событий, nnn — размер каталога, aaa — число допустимых объектов. При обычных предположениях об ожидаемой константной стоимости операций хеш-таблиц время работы составляет O(m+n+alog⁡a)O(m+n+a\log a)O(m+n+aloga), дополнительная память — O(m+n)O(m+n)O(m+n). Списки past и finishes сохраняются для прозрачности разбора. Потоковый подсчёт и предварительные агрегаты могут уменьшить затраты; их корректное обновление требует отдельной работы с временем и данными.

Ограничения baseline​

Счётчик зависит от прошлой политики показов и накопленного времени в каталоге. Он не различает число показов, вероятность отклика и интерес конкретного пользователя. Свежие объекты начинают с нуля; популярные получают преимущество. Пример также предполагает корректные, своевременно поступившие события и не выполняет полную валидацию данных.

Эти ограничения определяют дальнейшие задачи книги: анализ данных, временные протоколы, сильные baselines, персонализированные модели и корректная оценка. Здесь не утверждается, что счётчик оптимизирует неизвестную пользовательскую ценность.

Упражнения​

Упражнение · Граница публикации#

Какие условия доступности выполняются для E при now=9 и для F при now=12? Отдельно укажите, почему из этого ещё не следует место объекта в выдаче.

Разбор

E уже недоступна, поскольку правая граница исключительная. F доступна, поскольку левая граница включительная. Итоговый показ зависит также от истории пользователя, оценок других объектов и размера выдачи.

Упражнение · Проверка утечки#

Добавьте сто дочитываний D с временем 20. Убедитесь, что ответ при now=10 не меняется. Затем удалите временной фильтр и объясните изменение результата.

Ожидаемый результат

При сохранённом фильтре выдача остаётся B, C. Без фильтра будущие события повышают оценку D, и она попадает на первое место. Это искусственное преимущество получено за счёт информации, недоступной в момент решения.

Упражнение · Смена определения популярности#

Измените оценку: учитывайте число различных пользователей, дочитавших статью до now. Что произойдёт при повторных событиях одного пользователя? Какие части алгоритма можно оставить прежними?

Указание

Нужно считать множество пар (user_id, item_id) или отдельные множества пользователей для статей. Повтор одной пары не увеличивает оценку. Временной фильтр, доступность, пользовательский фильтр и выбор top-K сохраняют своё назначение.
