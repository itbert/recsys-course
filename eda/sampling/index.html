Выборка, фильтры и итоговый отчёт

Выборка меняет наблюдаемую структуру​

Для первичного анализа большого источника часто используется подмножество. До его построения нужно определить, выбираются ли события, аккаунты, объекты или интервалы времени. Эти схемы сохраняют разные свойства.

При выборке аккаунтов вместе со всей их доступной историей сохраняется последовательность внутри выбранного аккаунта, но сокращается поддержка объектов. При независимом отборе отдельных событий история разрывается. При выборе одного календарного дня сохраняется этот временной режим, но не вся сезонная или возрастная структура периода.

Если каждый показ независимо сохраняется с одной вероятностью qqq, то статья с nin_ini​ показами появится в выборке с вероятностью

P(i представлен)=1−(1−q)ni.\Prob(i\text{ представлен})=1-(1-q)^{n_i}.P(i представлен)=1−(1−q)ni​.

Действительно, её отсутствие требует совместного несохранения всех nin_ini​ показов; при предположенной независимости вероятность равна (1−q)ni(1-q)^{n_i}(1−q)ni​. При q=0,1q=0{,}1q=0,1 объект с одним показом сохраняется с вероятностью 0,1, с десятью — примерно 0,6513. Поэтому равномерность отбора показов не означает равномерности попадания объектов.

Сохранять по одинаковому числу строк на статью тоже допустимо для специального вопроса, но тогда необвешенное среднее по строкам больше не описывает исходную смесь трафика. Для восстановления популяционной характеристики нужно знать устройство отбора и соответствующие условия оценивания. Простой seed обеспечивает повторение выбора, а не репрезентативность.

Фильтрация по поддержке​

В рекомендательных экспериментах бывает полезно выделить область с достаточным числом различных связей. Например, потребовать, чтобы у каждого аккаунта было не менее kkk различных статей, а у каждой статьи — не менее kkk аккаунтов. Это ограничение двудольной поддержки из главы о разреженности, а не число повторных показов.

Одного прохода недостаточно. После удаления редкой статьи некоторые аккаунты потеряют соседей; после их удаления редкими станут другие статьи. Нужно пересчитывать степени до прекращения изменений.

Определение · k-core поддержки#

Для конечного простого двудольного графа и целого k≥1k\ge1k≥1 рассматриваем максимальный по включению подграф, в котором каждая оставшаяся вершина имеет степень не меньше kkk. Он может быть пустым. В нашей реализации удаляются рёбра, инцидентные вершинам текущей степени меньше kkk, до неподвижной точки.

Общая задача разложения графа по ядрам рассмотрена Batagelj и Zaversnik в An O(m) Algorithm for Cores Decomposition of Networks. Ниже используется более простая реализация повторными полными проходами; линейная сложность алгоритма статьи ей не приписывается.

Теорема · Результат последовательного отсечения#

Описанный алгоритм на конечном графе завершается. Его непустой результат имеет минимальную степень не меньше kkk и содержит любой подграф исходного графа с этим свойством. Следовательно, результат является единственным максимальным по включению ядром.

Доказательство

При изменяющем проходе удаляется хотя бы одно ребро, новые рёбра не добавляются. Поэтому число изменений конечно. В непустой неподвижной точке не осталось вершины с положительной степенью меньше kkk: иначе её рёбра удалились бы.

Пусть HHH — любой подграф с минимальной степенью не меньше kkk. В начале он содержится в исходном графе. Предположим, что он содержится перед очередным проходом. Степень каждой его вершины в текущем графе не меньше степени в HHH, то есть не меньше kkk. Поэтому ни одна вершина HHH и ни одно его ребро этим проходом не удаляются. По индукции весь HHH сохраняется до конца.

Итог сам удовлетворяет ограничению и содержит все другие допустимые подграфы. Два различных максимальных результата с такими свойствами существовать не могут.

□

В демонстрации из десяти связей остаются четыре — между двумя аккаунтами и двумя объектами. Плотность в исходном прямоугольнике 5×55\times55×5 равна 40%, в оставшемся 2×22\times22×2 — 100%. Это следствие отбора. Новый плотный набор не доказывает, что исходная задача была столь же хорошо наблюдаема.

Код и стоимость​

diagnostics.py — продолжение модуля
def k_core(edges, minimum=2):
    if type(minimum) is not int or minimum < 1:
        raise ValueError("minimum должен быть положительным целым")
    current, trace = set(edges), []
    while current:
        user_degree = Counter(user for user, _ in current)
        item_degree = Counter(item for _, item in current)
        remaining = {(user, item) for user, item in current
                     if user_degree[user] >= minimum and item_degree[item] >= minimum}
        trace.append({"edges_before": len(current), "edges_after": len(remaining)})
        if remaining == current:
            break
        current = remaining
    return current, trace


TOY_EDGES = {("u1", "A"), ("u1", "B"), ("u2", "A"), ("u2", "B"),
             ("u3", "B"), ("u3", "C"), ("u4", "C"), ("u4", "D"),
             ("u5", "D"), ("u5", "E")}

Сначала вход переводится в множество различных пар. Счётчики степеней строятся заново на каждом проходе. remaining содержит только связи, у которых оба конца проходят порог в текущем графе; обновление выполняется одновременно. trace сохраняет размеры до и после, включая заключительный неизменяющий проход для непустого результата.

При RRR проходах и MMM исходных рёбрах ожидаемая стоимость этой реализации — O(RM)O(RM)O(RM), память — O(M)O(M)O(M). Это прозрачный учебный алгоритм. На масштабе применяются структуры соседства и очередь изменившихся степеней, позволяющие не пересчитывать весь граф. Изменение реализации должно сохранять тот же объект фильтрации.

Отбор по всему периоду использует поддержку всего периода. Для обучающего эксперимента это может включать будущие взаимодействия относительно оцениваемых решений. Здесь он применяется как описательный анализ чувствительности конечного набора; допустимость подобного отбора в train/test задаётся отдельным протоколом части 6.

Воспроизводимый отчёт​

Следующий сборщик соединяет все введённые характеристики.

report.py
"""Воспроизводимый описательный отчёт; генератор не моделирует реальный трафик."""
from dataclasses import asdict
import hashlib
import json
from pathlib import Path
import platform
from dataset import generate, DAY, END
from diagnostics import k_core, user_profiles
from metrics import concentration, counts, rates, summary, support
from temporal import cohorts, daily


def build_report():
    rows, users, catalog = generate()
    user_counts = counts(rows, users, "user_id")
    item_counts = counts(rows, catalog, "item_id")
    pairs = support(rows)
    positive_pairs = support(rows, lambda row: row.label == 1)
    profiles = user_profiles(rows)
    flagged = {profile["user_id"] for profile in profiles if profile["review_flag"]}
    without_flagged = [row for row in rows if row.user_id not in flagged]
    core, trace = k_core(pairs, 3)
    payload = {"rows": [asdict(row) for row in rows], "users": users, "catalog": catalog}
    encoded = json.dumps(payload, sort_keys=True, separators=(",", ":"), allow_nan=False).encode()
    return {
        "manifest": {"synthetic": True, "python_version": platform.python_version(),
                     "observation_end_exclusive": END, "time_unit": "seconds", "days": 28,
                     "snapshot_cutoff_inclusive": END + 900, "outcome_horizon_seconds": 600,
                     "data_sha256": hashlib.sha256(encoded).hexdigest(),
                     "source_sha256": {name: hashlib.sha256(Path(__file__).with_name(name).read_bytes()).hexdigest()
                                       for name in ("dataset.py", "metrics.py", "temporal.py", "diagnostics.py", "report.py")}},
        "registry": {"users": len(users), "items": len(catalog),
                     "users_without_impressions": sum(count == 0 for count in user_counts.values())},
        "activity": summary(user_counts.values()),
        "popularity": concentration(list(item_counts.values())),
        "support": {"exposure_pairs": len(pairs), "observed_positive_pairs": len(positive_pairs),
                    "exposure_density": len(pairs) / (len(users) * len(catalog)),
                    "positive_density": len(positive_pairs) / (len(users) * len(catalog))},
        "signals": rates(rows), "daily": daily(rows), "cohorts": cohorts(rows),
        "diagnostics": {"flagged_ids": sorted(flagged), "profiles": profiles,
                        "daily_receipt_p90_seconds": [summary([row.received_at - row.event_time for row in rows if row.event_time // DAY == day])["p90"] for day in range(28)]},
        "sensitivity": {"without_flagged": rates(without_flagged),
                        "without_flagged_popularity": concentration(list(counts(without_flagged, catalog, "item_id").values())),
                        "core3_edges": len(core), "core3_trace": trace},
    }


if __name__ == "__main__":
    report = build_report()
    output = Path(__file__).with_name("report.json")
    output.write_text(json.dumps(report, ensure_ascii=False, indent=2, allow_nan=False) + "\n")
    print("Сохранён report.json; показов:", report["signals"]["impressions"])

Для повторения сохраните полный dataset.py из первой главы, последовательно приведённые части metrics.py, temporal.py, diagnostics.py и этот report.py в одной папке. Вызов python3 report.py создаёт report.json. Основная цепочка использует стандартную библиотеку Python 3.10 или новее; проверена на 3.13.3.

Данные сериализуются в фиксированном порядке ключей; хеш включает таблицу, реестры и каталог. Отдельно сохраняются байты пяти модулей и версия Python. Это позволяет установить, какие данные и преобразования дали конкретный отчёт. Хеш не подтверждает научную правильность выбранной постановки.

Из результата в следующий вопрос​

Установлено в синтетическом набореДопустимый следующий вопрос
Восемь аккаунтов не имеют показовКак реестр и период доступности влияют на показатель активности?
Три статьи концентрируют около 62,69% показовКакую роль играют доступность и механизм отбора кандидатов?
Плотности показов и положительной поддержки различаютсяКакую поддержку использует конкретный метод обучения?
В день 12 потеряна часть метокКакие анализы сохраняют интерпретацию при этом покрытии?
Один аккаунт имеет необычный временной и объектный профильКакой источник породил события и есть ли независимое подтверждение дефекта?
Фильтр меняет доли без смены моделиНа какую популяцию распространяется итоговый результат?

Отчёт должен отделять наблюдение, возможное объяснение и способ проверки. Фраза «после фильтра кликов стало больше в доле показов» является наблюдением о преобразованном наборе. Фраза «фильтр улучшил рекомендации» требует иного эксперимента и здесь не установлена.

Обнаружение зависимости после просмотра множества срезов полезно для выдвижения гипотез. Подтверждение на тех же выбранных по результату срезах не заменяет заранее определённую проверку на подходящих новых данных. Условия статистического сравнения будут введены вместе с протоколами оценки.

Упражнения​

Упражнение · Редкий объект в подвыборке#

Каждый из пяти показов статьи независимо сохраняется с вероятностью 0,2. Найдите вероятность увидеть статью хотя бы раз. Равна ли она вероятности сохранения отдельного показа?

Разбор

Вероятность равна 1−0,85=0,672321-0{,}8^5=0{,}672321−0,85=0,67232, а для одного показа — 0,2. Единица выборки определяет механизм включения; вероятности для событий и объектов различаются.

Упражнение · Один проход фильтра#

В интерактивном графе каждый аккаунт сначала имеет степень 2, а только объект E — степень 1. Почему удаление одного E ещё не даёт 2-core? Что потеряется при использовании числа показов вместо степени?

Разбор

После удаления E аккаунт u5 теряет одну из двух связей и тоже должен быть удалён; затем каскад распространяется через D, u4, C и u3. Повторные показы одного объекта не создают новых соседей. Порог по их числу выделил бы иной набор, не удовлетворяющий определению степени поддержки.
