Разреженная реализация и сложность

Хранение наблюдений​

У плотного профиля U×IU\times IU×I память растёт вместе с произведением числа пользователей и объектов. При MMM наблюдённых уникальных пар словари множеств и перевёрнутый индекс хранят O(M+U+I)O(M+U+I)O(M+U+I) записей. Явные рейтинги хранят значения по тому же принципу. CSR удобно обходить по строкам, CSC — по столбцам. Битовые множества подходят, если размер индексов и плотность операций оправдывают выделенную память. Форматы и инварианты маски подробно разобраны в части 2.

Построение item-графа​

Пусть корзина bbb содержит dbd_bdb​ уникальных объектов. Цикл пар выполняет

∑b(db2)\sum_b \binom{d_b}{2}b∑​(2db​​)

обновлений, помимо прохода по объектам и сортировки внутри каждой корзины. Он хранит до PPP различных неупорядоченных пар. После отсечения top-LLL в serving остаётся не более ILILIL исходящих дуг, но создание всех пар до отсечения требует O(P)O(P)O(P) памяти. При популярной корзине итоговая матрица X⊤XX^\top XX⊤X может стать плотной даже для разреженного XXX. Измеряйте рост размера проекции отдельно от исходной матрицы.

Список длины LLL можно поддерживать кучей по каждой строке: O(Plog⁡L)O(P\log L)O(PlogL) времени для пар при L≥2L\ge2L≥2 и O(IL)O(IL)O(IL) памяти для самих куч. Это не устраняет потребность сначала получить корректно агрегированный счётчик каждой пары. Для больших данных пары агрегируют по блокам или группируют по ключу во внешней памяти. Раннее удаление малых частичных счётчиков способно потерять пару, которая стала бы частой после объединения блоков.

Рекомендация при hhh элементах истории выполняет до hLhLhL прибавлений. В учебном коде финальная сортировка просматривает весь допустимый каталог. В production можно сортировать только полученные кандидаты и дозаполнять top-KKK из заранее упорядоченного глобального списка. Чтобы получить тот же результат, нужно сохранить сравнение по соседскому score, популярности и ID, а также дубли и фильтры обработать до возвращения выдачи.

Поиск user-соседей​

При длинах posting lists did_idi​ запрос обходится примерно в ∑i∈Pudi\sum_{i\in P_u}d_i∑i∈Pu​​di​ накоплений. Стоимость зависит от популярности истории. Один частый объект может затронуть почти весь индекс. Отсечение или изменение его веса не тождественны: вес уменьшает вклад отдельной записи, а исключение ещё и сокращает расчёт. После отбора пользователей затраты на голосование пропорциональны суммарным размерам их профилей.

Параллельные подсчёты и приближённый поиск меняют инженерную реализацию. Для приближённого варианта публикуют совпадение с точным списком соседей и сквозные метрики. Быстро найденные близкие по выбранной мере пользователи ещё могут иметь мало пригодных объектов. В отчёте отдельно полезны средний и верхние квантили задержек по длине истории.

Упражнение · Профиль большого размера

Сто корзин содержат по 5 объектов и одна содержит 100. Сравните число обновлений пар от большой корзины и остальных вместе.

Разбор

Сто малых дают 100⋅10=1000100\cdot10=1000100⋅10=1000 обновлений. Большая даёт 4950. Её доля в обработке обновлений около 83%, хотя корзина одна из 101.

Упражнение · Совпадение по одной координате

Если у всех аккаунтов присутствует объект A, уменьшится ли время обхода posting list A при применении inverse user frequency?

Разбор

Длина списка не меняется. В выбранной формуле вес A равен 1, поэтому уменьшается его относительный вклад по сравнению с редкими координатами. Для сокращения времени нужны иные операции, например заранее определённое отсечение.
